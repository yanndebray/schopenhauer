# Executive Summary

Schopenhauer v0.2.0 is a ~650 lines-of-new-code orchestration layer on top of Pandoc.
It adds a render pipeline, Jinja2 preprocessing, YAML spec compilation, and a CLI.
Pandoc does all the actual rendering.

This report takes the concrete use case of compiling a 9-chapter, 18,000-word book
from Markdown to `.docx` and asks: **was Schopenhauer worth it?**

The honest answer: for *this* use case, barely. For the *intended* use case —
AI-agent-driven document generation with data binding — the architecture is sound
but the features aren't there yet.

# Part 1: What Schopenhauer Actually Is

## The Pipeline

```
Markdown + YAML frontmatter
        |
  render.py — detect input, extract frontmatter, merge variables
        |
  preprocess.py — Jinja2 {{variable}} substitution
        |
  pandoc_backend.py — pypandoc wrapper
        |
  Pandoc (bundled via pypandoc-binary)
        |
  .docx / .pdf / .html / .pptx / .epub
```

## Code Inventory (v0.2.0 — new modules only)

| Module | Lines | What it does |
|--------|-------|-------------|
| `render.py` | 222 | Orchestration: input detection, frontmatter, variable merging, template resolution |
| `spec_compiler.py` | 227 | Legacy YAML/JSON spec → Markdown compiler |
| `pandoc_backend.py` | 140 | pypandoc wrapper with format-specific defaults |
| `preprocess.py` | 63 | Jinja2 `{{var}}` substitution with passthrough undefined |
| `cli.py` (additions) | ~50 | `will render` command |
| **Total new code** | **~700** | |

The legacy python-docx code (`core.py`, `document.py`, `templates.py`, `styles.py`, `api.py`)
adds another ~3,500 lines but is being phased out.

## What Each Layer Actually Does

**render.py** — The genuine value-add:

- Detects `.md` vs `.yaml`/`.json` input and routes accordingly
- Extracts YAML frontmatter, strips the `will:` namespace, keeps only Pandoc-native keys
- Merges variables from frontmatter + CLI (CLI wins)
- Resolves template names → reference doc paths
- Delegates to Pandoc for all rendering

**pandoc_backend.py** — Mostly pass-through:

- Adds `--standalone` automatically
- Adds `--pdf-engine=xelatex` for PDF
- Adds `--embed-resources` for HTML
- Manages temp files for byte returns
- ~80% is pypandoc glue

**preprocess.py** — Currently minimal:

- `{{var}}` → value substitution via Jinja2
- Unresolved variables pass through as-is
- No loops, conditionals, or includes yet (planned for v0.2.x)

**spec_compiler.py** — Backward compatibility:

- Converts legacy YAML/JSON section specs to Markdown
- 9 section type compilers (heading, table, image, quote, code, etc.)
- Users who emitted structured YAML specs keep working

# Part 2: The Book Use Case — Reality Check

## What Happened

We compiled "Programming with Claude Code" — 9 chapter Markdown files, ~18,000 words —
into a single styled `.docx` using a reference template from an existing Word document.

## What Schopenhauer Did

```bash
will render book.md -o book.docx -t template.docx
```

This translated internally to:

```bash
pandoc book.md -o book.docx --standalone --reference-doc=template.docx
```

That's it. The preprocessing pipeline was a no-op (no `{{variables}}` in the book).
The spec compiler was unused. The template registry was unused.

## What Schopenhauer Did NOT Do

| Task | Who did it | Schopenhauer involved? |
|------|-----------|----------------------|
| Chapter assembly (9 files → 1 file) | Manual scripting | No |
| Frontmatter stripping per chapter | Manual scripting | No |
| Page breaks between chapters | Manual `\newpage` insertion | No |
| Reference doc template creation | Existing Word file | No |
| Font size debugging (12pt → 10pt) | python-docx directly | No |
| Table of contents | Not done (Pandoc has `--toc`) | Not exposed |
| Chapter numbering | Not done (Pandoc has `--number-sections`) | Not exposed |

## What Raw Pandoc Could Have Done Better

Pandoc natively accepts multiple input files:

```bash
pandoc chapters/00-introduction.md \
       chapters/01-before-claude-code.md \
       chapters/02-first-contact.md \
       ... \
       -o book.docx \
       --standalone \
       --reference-doc=template.docx \
       --toc \
       --number-sections \
       -M title="Programming with Claude Code" \
       -M author="Yann Debray"
```

This would have:

- Eliminated the manual chapter assembly step
- Added a table of contents automatically
- Added chapter numbering automatically
- Given full access to all Pandoc flags

Or with a **Pandoc defaults file** (`book.yaml`):

```yaml
input-files:
  - chapters/00-introduction.md
  - chapters/01-before-claude-code.md
  - chapters/02-first-contact.md
  - chapters/03-philosopher-tools.md
  - chapters/04-competitive-intelligence.md
  - chapters/05-mcp-revolution.md
  - chapters/06-side-projects.md
  - chapters/07-writing-the-future.md
  - chapters/08-what-this-relationship-is.md
output-file: book.docx

standalone: true
```

# Part 3: Competitive Landscape

## The Players

### Quarto — The 800-Pound Gorilla

- ~900,000 lines of TypeScript on Deno, backed by Posit (company)
- Bundles Pandoc + adds computational execution (Python/R/Julia), cross-references,
  layout system, citations, project management, visual editor
- The dominant tool in scientific publishing

**Strengths**: Feature-complete, well-funded, large community, IDE integration.

**Weaknesses**: Massive complexity for non-scientific use cases. 200MB+ install.
No Python API — it's a CLI tool built in TypeScript. Opaque processing: hard to know
what it does to your Markdown before Pandoc sees it. Overkill for "Markdown → docx."

### pypandoc — The Raw Building Block

- ~2,000 lines of Python, 3.8M PyPI downloads/month
- Two functions: `convert_file()` and `convert_text()`
- `pypandoc_binary` bundles Pandoc for zero-config install

**Strengths**: Dead simple. Does one thing well. Schopenhauer's foundation.

**Weaknesses**: No templates, no preprocessing, no CLI, no opinions.
The gap between pypandoc and a useful tool is everything Schopenhauer adds.

### Typst — The Exciting Newcomer

- Modern typesetting system in Rust. 38,000+ GitHub stars.
- Millisecond compilation (vs. seconds/minutes for LaTeX)
- Native data loading from JSON/CSV, built-in scripting (loops, conditionals)
- Pandoc can output to Typst format → 27x faster PDF than LaTeX path

**Strengths**: Blazing fast. Native data binding. Clean syntax. PDF/UA-1 compliant.

**Weaknesses**: **PDF only** — no docx, html, pptx. Not Markdown. Own ecosystem.

# Part 4: Honest Pros and Cons

## What Schopenhauer Gets Right

**1. The architecture is correct.**
Markdown as source of truth → preprocessing → Pandoc rendering.
This is exactly how Quarto works, minus the computational execution.
The layering is clean: render.py orchestrates, Pandoc renders.

**2. pypandoc_binary for zero-config.**
Users `pip install schopenhauer` and get Pandoc bundled. No separate install.
This is a genuine friction reducer.

**3. YAML spec backward compatibility.**
The spec compiler means v0.1.x users aren't abandoned.
Structured YAML/JSON input is also ideal for AI agents that emit JSON.

**4. The thin wrapper is a feature, not a bug.**
700 lines of code means less to maintain, less to break, less to understand.
Quarto's 900k lines is a cautionary tale.

**5. Python-native.**
`from will import render` — usable as a library. Quarto and Typst can't do this.

## What Schopenhauer Gets Wrong (or Hasn't Done Yet)

**1. Missing the key differentiators.**
The features that would justify Schopenhauer over raw Pandoc are all "planned":

- Data binding with loops and conditionals
- MCP server for AI agents
- JSON Schema validation
- `{{include}}` for file composition
- `{{table:csv_file}}` for data-driven tables

Without these, the value over `pandoc` CLI + a defaults file is marginal.

**2. The CLI doesn't expose critical Pandoc features.**
No `--toc`, `--number-sections`, `--lua-filter`, `--extract-media`, or
`--extra-args` pass-through. Users hit a wall quickly and fall back to raw Pandoc.

**3. No multi-file input.**
Pandoc natively handles `pandoc file1.md file2.md file3.md -o book.docx`.
Schopenhauer requires manual assembly into a single file.
For a tool aimed at books and reports, this is a significant gap.

**4. Template system is empty.**
Template *resolution* works (name → path), but only one reference doc exists (`book.docx`).
The planned templates (report, memo, letter, academic, proposal, contract) don't exist as
Pandoc reference docs. The 15 TemplateConfig objects in `templates.py` are python-docx
legacy configs that don't work with the Pandoc pipeline.

**5. No reference doc management.**
The font size debugging (10pt vs 12pt) exposed a real gap: Schopenhauer doesn't
inspect, validate, or help manage reference doc styles. Users need python-docx
or Word to debug template issues. A `will template inspect template.docx` that
shows style definitions would have caught the Body Text vs Normal mismatch instantly.

**6. The legacy code is dead weight.**
~3,500 lines of python-docx code (`core.py`, `document.py`, `templates.py`, `styles.py`)
still ship with the package but are being deprecated. Until Phase 3 removes them,
the codebase sends mixed signals about what Schopenhauer actually is.

# Part 5: Where the Real Value Lives

## The Uncontested Niche

No existing tool targets **programmatic AI-agent document generation from Markdown
with template management and data binding**:

- Quarto is for human scientists, not AI agents
- pypandoc is plumbing, not a product
- Typst is PDF-only and non-Markdown
- Sphinx is for software docs
- Existing Pandoc MCP servers are bare format converters

Schopenhauer's strongest differentiator is the **agent interface**:

1. **JSON Schema for inputs** — LLMs can validate specs before submission
2. **MCP server** — `generate_document`, `list_templates`, `inspect_document`
3. **Structured spec input** — AI agents emit JSON/YAML naturally
4. **Variable substitution** — data binding from external sources
5. **Python API** — `render("spec.yaml", output="report.docx")` in agent code

None of these exist yet (except basic variable substitution), but the architecture
supports them.

## What Would Make Schopenhauer Indispensable

Ranked by impact:

1. **Data binding** — `{{for row in data}}`, `{{if condition}}`, `{{table:metrics.csv}}`
   This is the feature that justifies the preprocessing layer.

2. **Multi-file input** — `will render chapters/*.md -o book.docx`
   Pandoc already supports this; Schopenhauer should too.

3. **Pass-through Pandoc args** — `will render file.md -o out.docx -- --toc --number-sections`
   Don't limit users to what the CLI explicitly exposes.

4. **Reference doc inspection** — `will template inspect template.docx`
   Show all style definitions so users can debug before rendering.

5. **MCP server** — The killer feature for the AI agent use case.

6. **Real templates** — Ship 5-7 reference docs with the package (report, memo, letter, etc.)

## The Typst Opportunity

Pandoc can output to Typst format. Typst compiles to PDF **27x faster** than LaTeX.

```
Markdown → Pandoc → Typst → PDF  (fast)
Markdown → Pandoc → LaTeX → PDF  (slow)
```

Adding `--pdf-engine=typst` support to `pandoc_backend.py` would give Schopenhauer
dramatically faster PDF generation with a ~40MB additional dependency.
